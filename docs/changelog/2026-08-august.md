# HelloRun Changelog — August 2026

## August 7 — Runners can ask to cancel

- A runner can now ask to cancel a registration from their registrations page.
  It records the ask and tells the organiser; it does **not** cancel.
- That split is deliberate. Cancelling a paid registration decides what happens
  to the money, and that is the organiser's call — not something to infer from a
  runner tapping a button. The runner-facing copy says plainly that nothing is
  cancelled and no refund is issued automatically; the organiser's roster shows
  the request with "Nothing is cancelled until you do it below, including
  anything owed back", right beside the existing cancel action.
- Requests are refused when the registration is not live, and cannot be repeated.
  The lookup is scoped to the signed-in runner, so one runner cannot request
  against another's registration.
- Added a `registration.cancellation_requested` communication event **with its
  email sender wired**, having hit exactly that gap on the previous event.
- No migration: the two new Registration fields are optional.
- Unit suite 1127/1127.

## August 7 — Race-day staff can be delegated per event

- Until now, checking runners in required the organiser's own login on the
  organiser's own phone. An event can now have assigned staff with named
  permissions: `check_in` (check-in, scanning, bibs), `race_kit`, and `results`.
- Deliberately **not** a new value on `User.role`. That field is global and
  checked in dozens of places; widening it would grant something everywhere to
  solve a problem that exists on one event. `EventStaff` scopes a grant to a
  single event, and revoking is one write.
- `requireOnsiteEventAccess(permission)` is a sibling of
  `requireOrganizerEventAccess`, not an edit to it: the original rejects anyone
  who is not an organiser or admin before any per-event check runs, and race-day
  volunteers are ordinary runner accounts. Widening the original would have
  loosened every route using it.
- Staff reach only the onsite routes wrapped in the new guard, each asking for the
  permission its job needs. The staff-management screens stay organiser/admin
  only, so staff can never grant access to themselves or anyone else.
- Permissions are an allowlist, so a crafted form post cannot invent one.
  Revoking keeps the row, leaving who-had-access-when answerable after the event;
  re-adding someone previously removed reinstates them rather than colliding with
  the unique index. Granting requires an existing account — this grants access, it
  does not create accounts.
- No migration: a new Mongo collection needs none, and `User.role` is untouched.
- Unit suite 1122/1122.

## August 7 — Results import from a spreadsheet

- Organisers can import results from a `.csv` or `.xlsx`. Most of this already
  existed and was unreachable: `result-import-validation.service.js` had full row
  validation, error categorisation and error-CSV generation but was imported by
  nothing, and `webhooks/timing-system.js` held the only row-processing logic,
  behind a signature-gated machine endpoint. `exceljs` already reads both
  formats, so no parser package was added.
- Preview then commit — the file is parsed and validated with nothing written,
  and only rows that passed are offered. Header matching is lenient because
  timing exports disagree wildly ("Bib No", "RACE NUMBER", "Chip Time", "Gun
  Time" all resolve); unknown columns are ignored and blank spacer rows skipped
  rather than reported as errors. Rejected rows download as a CSV.
- Imported results land as **submitted**, never auto-approved: approving is what
  places a runner on the leaderboard, so it stays deliberate. Rows apply
  independently, so one unknown bib cannot discard a field's worth of results.
  Capped at 2000 rows with truncation reported rather than silent.
- **Walk-in registration was skipped, not forgotten.** It is not code-only:
  `Registration.userId` is `required: true` and a genuine walk-in has no account,
  so it is blocked by the same constraint as guest registration. Only an
  account-holder variant could ship today, which would be a confusing feature, so
  it waits for the guest work.
- Unit suite 1111/1111.

## August 7 — Race pass, bib scanning, and registration cancellation

- **Runners can see their own bib and check-in code.** New race pass at
  `/my-registrations/:registrationId/race-pass`, scoped to the signed-in runner
  so one pass cannot be read from another. Onsite entries link to it from the
  registrations list; virtual ones do not. Previously the QR endpoints were
  organiser-only, so the scanning half of race day had nothing to scan.
- **The bib QR no longer leaks database ids.** It carried
  `EVENT:{mongoId}|BIB:{n}|TIME:{ts}` in plaintext, so anyone who photographed a
  bib learned a live event id and nothing stopped them editing it into another
  bib. It now carries an opaque AES-256-GCM token that reveals nothing and fails
  closed if altered. `token-encryption.service.js` gained purpose-scoped key
  derivation rather than a second crypto envelope; Strava keeps its own key and
  call signature. Codes printed before the change still scan — `resolveScannedQr`
  accepts both and reports which it saw. Revocation still needs a token store and
  remains queued behind migration `023`.
- **Bib scanning** via `POST /organizer/events/:eventId/check-in/scan`, answering
  the cases staff hit at a start line with typed outcomes: `checked_in`,
  `already_checked_in`, `cancelled`, `wrong_event`, `unknown_bib`, `invalid`.
  Payment is a warning rather than a refusal — many events settle at the desk.
  Bib lookup for scanning is an exact match, deliberately separate from the
  roster's partial search: resolving "10" to bib "101" would check in the wrong
  runner. Scanning uses the browser's `BarcodeDetector`; browsers without it
  (Safari today) get manual code entry rather than a broken camera panel.
- **Registration cancellation.** `cancelled`/`refunded` were valid statuses that
  nothing ever set. Cancelling now frees the category slot, voids the bib so the
  number can be reissued, stops any check-in counting, records who/when/why with
  an audit event, and notifies the runner through a new `registration.cancelled`
  communication event. Offered only for live registrations, behind the shared
  high-risk confirmation. Runner-initiated cancellation needs an
  organiser-configurable policy and is not included.
- Unit suite 1102/1102.

## August 7 — Onsite results now reach rankings, leaderboards, and certificates

- Closed the onsite finisher dead end. An approved onsite result previously awarded a
  badge and nothing else: `ranking.service.js` requires `mongo_submission_id`,
  `leaderboard.service.js` queries the Mongo `Submission` collection, and no
  certificate path was onsite-aware — and onsite results created no Submission.
- An approved onsite result is now materialised as an approved `Submission` via
  `onsite-result-submission.service.js`, so every existing consumer works unchanged.
  **No schema change was needed**: `Submission.participationMode` already carried
  `'onsite'` and `leaderboard.service.js` already filtered on it — it was waiting for
  rows that never arrived. The alternative, teaching ranking, leaderboard and
  certificate code to read `onsite_results` directly, would have forked three services
  and left every future consumer to remember both sources.
- Extracted `applyApprovedSubmissionEffects` in `submission.service.js` — leaderboard
  cache, certificate, notification, achievements, milestones and ranking sync — and
  used it for both virtual review and onsite approval, so the two cannot drift.
- Distance is resolved from the recorded result, then the race category, then the
  registration's distance label. When none of them knows, approval reports that the
  result did not enter the results rather than inventing a distance that would feed a
  ranking. Signed labels such as `-5K` are refused instead of parsing as 5.
- Marshal-recorded finishes store `proofType: 'manual'` with a plain note rather than
  fabricated proof metadata. Re-approving updates the existing submission, which the
  unique `registrationId` index already enforced.
- Materialisation failures are surfaced, not swallowed: the Postgres approval is
  already committed by then, so the endpoint returns `submissionCreated` plus a reason
  and the results page shows it, instead of implying a finisher is ranked.
- Guest registrations are explicitly rejected here with a clear message — they have no
  runner to rank. Relevant once guest registration exists.
- Unit suite 1084/1084.

## August 7 — Live check-in board, onsite results UI, and real Phase 7 test coverage

- Added the live check-in board (`/organizer/events/:eventId/check-in/board`). The
  entire realtime API already existed and was unreachable. First paint is
  server-rendered and the page then polls, so a dropped connection leaves the
  last known figures on screen with a staleness notice rather than blanking.
- Fixed a **broken query** that made the dashboard endpoints 500:
  `getCheckInVelocity` used `INTERVAL '${windowMinutes} minutes'`, which places a
  bound parameter inside a string literal — Postgres received
  `INTERVAL '$1 minutes'` and rejected it. Now uses `make_interval(mins => ...)`.
- Fixed a fabricated estimate: `estimateCheckInCompletion` defaulted the recent
  check-in count to 1 when there were none, producing a confident completion time
  out of nothing. It now reports no estimate when there is no basis for one.
  Realtime totals are also scoped to onsite registrations so the board agrees
  with the check-in console.
- Added the onsite results page (`/organizer/events/:eventId/onsite-results`) for
  recording finish times and approving results. Finish times are validated and
  converted to milliseconds server-side, which wires up
  `result-import-validation.service.js` — 258 lines that were imported by nothing.
  The page states plainly that approval currently awards badges only and does not
  yet reach the leaderboard or certificates.
- Fixed `decodeQRData`, which returned `success: true` for any input that did not
  throw — `'garbage'` decoded "successfully" with undefined ids and a `NaN`
  timestamp. It now requires EVENT, BIB and a numeric TIME, and splits on the
  first colon so values containing one survive.
- **Deleted `tests/phase7-extended.unit.test.js` and
  `phase7-extended-fixed.unit.test.js`** — 621 lines that imported zero
  application code, building mock objects and asserting on the mocks. They
  contributed ~30 passing tests while providing no regression protection, in the
  exact area being extended. Both bugs above were sitting under that coverage.
  Replaced with `tests/onsite-result-validation.unit.test.js`, which exercises the
  real validator and QR helpers.
- Linked the onsite pages from the organiser event-details tools grid, gated on
  `supportsOnsiteOperations`, so they are no longer reachable only by direct URL.
- Unit suite 1074/1074 (net change reflects removing the placebo tests).

## August 7 — Organizer race-day check-in console; onsite uniqueness fixes

- Reviewed the proposed onsite implementation pack and found its premise out of
  date: onsite events already ship (`Event.eventType` `virtual|onsite|hybrid`,
  `Registration.participationMode`, bibs, check-ins, race kits, result imports,
  QR generation, timing webhook). Filed the review and moved the pack to
  [onsite-registration-expansion](../features/onsite-registration-expansion/README.md)
  with a preface marking its architecture, data-model, and status sections
  superseded. The real gap was that **no organiser UI existed** for the eight
  live onsite endpoints.
- Fixed two correctness defects in the Phase 7 onsite tables via additive
  migration `023_onsite_checkin_bib_uniqueness.sql`: `check_ins` had no
  uniqueness on `(event_core_id, registration_id)`, so a repeated scan inserted a
  second row and inflated `v_event_checkin_summary`; and `assignBib`'s
  `ON CONFLICT (mongo_bib_assignment_id)` never fired (the INSERT omits that
  column, and Postgres does not treat NULLs as conflicting), so a registration
  could accumulate multiple live bibs. The migration reconciles existing
  duplicates first, keeping the earliest row and voiding surplus bibs.
- `recordCheckIn` now upserts and reports `was_already_checked_in`, preserving
  the original arrival time; `assignBib` targets the new live-bib partial index
  so voiding then reassigning still works.
- Added the organiser check-in console at
  `GET /organizer/events/:eventId/check-in`: mobile-first participant search by
  name, email, confirmation code, or bib; check-in action; payment and
  already-checked-in warnings; and a CSV backup participant list for weak
  venue connectivity. Linked from the registrants page for onsite events.
- Registrations whose Postgres shadow row has not synced are surfaced as
  "Not synced" rather than silently omitted, because check-in cannot be recorded
  for them.
- Headline check-in progress is event-wide, computed independently of the active
  search and page limit; the earlier draft derived it from the returned rows,
  which would have understated progress on any event larger than one page. When
  the Postgres totals query fails the figures degrade to an em dash and an
  explanatory notice rather than a misleading zero.
- Rate-limited the check-in endpoint and the backup-list download.
- Added the bib assignment page (`/organizer/events/:eventId/bibs`): per-row
  assign/update, plus a preview-then-confirm sequential range that only touches
  listed participants who have no bib and whose record has synced. Backed by a
  new bounded, rate-limited `POST /events/:eventId/bibs/assign-bulk` that
  attempts each row independently and returns per-row outcomes, so one duplicate
  bib cannot discard the batch.
- Added the race-kit release page (`/organizer/events/:eventId/race-kits`) and
  `markRaceKitReleased`. The Phase 7 schema has no per-participant kit record, so
  pickup is recorded on the bib assignment; the page states that a bib is
  required rather than failing at the point of release. Repeat releases preserve
  the original pickup time.
- Generalized the roster read model to `onsite-roster.service.js`, now shared by
  all three onsite pages so a participant looks identical on each; route file
  renamed to `onsite-pages.js`. The three pages cross-link.
- Added `tests/organizer-onsite-operations-ui.unit.test.js` (16 DB-free tests)
  and integration regression tests for the upsert, reassignment, bulk-assignment
  and kit-release paths. Unit suite 1091/1091.
- **Deploy ordering:** migration `023` must be applied *before* this code is
  deployed. The upsert paths reference the new indexes as `ON CONFLICT` targets
  and will error if the migration has not run. Not yet applied — no approved
  non-production database exists.

## August 6 — Public event-details 500 for signed-out visitors (fix verification + regression coverage)

- Diagnosed a production `HTTP 500` on `GET /events/:slug` affecting every
  signed-out visitor to every event. Root cause: `isOwnOrganizerEvent(user = {},
  ...)` in `src/utils/workspace.js` used a default parameter (applies only to
  `undefined`), so a guest's `res.locals.user === null` reached `user.role` and
  threw; the throw was caught in `getEventDetails` and rendered as the generic
  500 page.
- The code fix already shipped in commit `b70b50d` (`const safeUser = user ||
  {}`); the live outage was a **deploy gap** — production was still serving the
  prior commit `f1f1b46`, which introduced the crashing call. `b70b50d` is a
  code-only change and requires no database migration (migration `022` belongs
  to the already-deployed `f1f1b46`).
- Added regression coverage: null/undefined-user cases for `isOwnOrganizerEvent`
  in `tests/workspace-switching.unit.test.js`, and a DB-free
  `tests/event-details-guest-render.unit.test.js` that drives the real
  `getEventDetails` with a guest request and asserts a 200 render.
- Deploy action (redeploy `b70b50d` and verify a signed-out `HTTP 200`) tracked
  for the auto-deploy pipeline.

## August 3 — Organizer and runner workspace switching

- Added session-based Runner and Organizer workspaces without changing the
  account's permanent role or creating duplicate user records.
- Allowed verified, unrestricted organizers to use the existing runner
  dashboard, registrations, submissions, notifications, groups, Strava, and
  participant shop tools.
- Added CSRF-protected desktop and mobile workspace switches and workspace-aware
  navigation, proof controls, public-page actions, and login redirects.
- Blocked organizers from registering, paying, or submitting results for events
  they manage while preserving participation in other organizers' events.
- Added focused unit and integration coverage for workspace eligibility,
  switching, redirect behavior, and participation conflicts.

## August 3 — Step-based accumulated competitions

- Added distance, steps, and dual-metric accumulated challenges with one
  official primary ranking metric and optional event-wide step goals.
- Added organizer create/edit, proof validation, OCR review, Strava
  compatibility, progress, shared-rank leaderboard, reporting, certificate,
  and milestone-badge behavior.
- Added additive PostgreSQL fields and constraints, MongoDB shadow-sync
  support, ranking sync, and an idempotent legacy distance-default backfill.
- Preserved legacy `accumulated_distance` and distance leaderboard aliases.
- Added `FEATURE_STEP_COMPETITIONS_ENABLED`, disabled by default until
  migrations, backfill, production smoke tests, and monitoring gates pass.
- Added focused repository tests and the canonical implementation record at
  [the step-competition feature plan](../create_event/step-competition-feature-plan.md).
