# HelloRun Changelog — August 2026

## August 8 — Category capacity actually works, plus four safety fixes

- **Race-category capacity has never been enforced, on any event.**
  `getRaceCategoryOptions` built the identifier as
  `String(category._id || category.categoryId || …)` — `_id` won, and Mongoose mints one for
  every subdocument — while `reserveCategorySlot` matched the `categoryId` slug. They never
  matched, so the reservation returned "no limit" and every registration sailed past. An
  organiser could set a 200-slot cap and take 5,000 entries.
- It was wider than capacity. Five other places compare `pricingSnapshot.raceCategoryId`
  against the slug and so never matched either: the accumulated-challenge target, the
  minimum submission distance, the onsite result distance, the slot release on cancellation,
  and the recount. All have distance-label fallbacks, which is why nobody noticed — they
  degraded rather than failed. `distancePricing[].categoryId` is a slug too, so per-category
  pricing was surviving on its label fallback and already disagreed with the public event
  page, which matches by slug. Fixing the identifier repairs all of them at once.
- **Capacity is now claimed on every pricing mode, not just distance-based.** A free event —
  or one priced by signup option or package — resolved no category at all and reserved
  nothing, so its `slots` were decoration. The category is resolved once, up front, and
  carried into all four branches; the amount logic is untouched.
- **The counter survives an organiser save.** `reserved` is not on the form, so rebuilding
  `raceCategories` handed a full category its capacity back on every unrelated edit —
  changing the submission deadline restored full capacity. `mergeRaceCategories` now carries
  it forward, the same way `mergeKitInventory` already did for kit stock.
- **A full category is visible before the form is submitted.** It used to be discoverable
  only by filling everything in and being rejected. The picker now disables it, labels it
  "Full", shows "N slots left" when it is nearly gone, and points at the waitlist where the
  event keeps one. It reuses `categoryIsFull`, so the form cannot disagree with the
  reservation.
- **The recount matches every shape the identifier has ever had** — the slug, the
  subdocument `_id`, and a bare distance label for rows that never resolved a category.
  Without that it would have scored every category zero and reset the counters it was meant
  to seed. The backfill script now delegates to the service instead of carrying its own copy
  of the query, which is how that service function became dead code. Available as
  `npm run capacity:recount`.
- Measured before shipping: 369 events, **0 with a capped category**, so there is no
  retroactive lockout — the dry run reports nothing to change.

### Four safety fixes

- `src/routes/organiser/onsite-pages.js` rendered `errors/404`, a view that does not exist,
  so that 404 reached the user as a **500**. Every other 404 in the file was already correct.
- **`POST /login` had no CSRF protection**, alone among auth POSTs. The form already sends
  the token, so enabling it changes nothing else.
- **Offer and transfer links no longer reach the logs.** The timeout and 404 loggers wrote
  `req.url` verbatim, filing live credentials that both route files promise are never logged.
- Five swallowed `catch (_) {}` now log. Each turned a query failure into a plausible but
  false screen: an empty audit trail, every badge at 0 earned, every event showing as
  un-saved. Two of them named variables that were not in scope in my first pass — caught by
  executing the catch bodies rather than trusting a syntax check.

## August 8 — Correctness fixes found by auditing the features just shipped

An audit of guest registration, waitlist, kit inventory and transfers — all live
in production as of this morning — found six data-integrity defects and one
pre-existing authorisation hole. Each was verified against the code before being
fixed, and each fix was verified live on a throwaway event.

- **Cross-event writes are no longer possible.** `assignBib`, `recordCheckIn` and
  `recordOnsiteResult` resolved the registration by id alone, with no join to the event.
  The route guard checks the organiser owns the *event*, so an organiser — or a volunteer
  with `check_in` on their own event — could POST another organiser's `registrationId` and
  write a bib, a check-in, or an **approved result** against their event, which awards
  achievements and materialises a submission for somebody else's runner. All three now
  scope by `event_core_id`, matching the join `markRaceKitReleased` in the same file
  already used.
- **Approving a transfer no longer destroys the recipient's own details.** The approval
  route synthesised a form with an empty emergency contact and a made-up waiver signature,
  because `acceptTransfer` only ever persisted name, email and mobile. On the **default**
  path — approval is on by default — that left the new runner with no emergency contact on
  race day, a waiver bearing a signature they never typed, and the departing participant's
  kit size. What the recipient supplies is now stored on the transfer as `acceptedDetails`
  and read back at completion; both the approval and auto-approve paths use that one source.
- **A waitlist claim can no longer register into a different category than the one
  offered.** The offer form was a free select over every distance. Somebody offered a 10K
  slot could pick 21K: 21K oversold, and the 10K slot stranded permanently because
  `markPromoted` clears `slotHeld`. The category now comes from the entry and overrides
  anything posted, the form shows it read-only, and `skipCapacityReservation` is
  conditional on the offer actually holding a slot.
- **A blank category no longer bypasses the waitlist fullness check.** Both guards were
  written `if (categoryId && …)`, so omitting the hidden field skipped them — and the
  resulting entry could never be promoted, since promote buttons are built per category.
  Blank is now refused when the event has capped categories. Existing orphans are labelled
  on the organiser page so they can be seen and withdrawn.
- **The claim path honours the event's own rules.** It never called
  `getGuestRegistrationBlock`, so an account-only event could yield a guest registration
  through the waitlist, and an offer window of up to 336 hours could be claimed after
  registration closed. Checked now on both the GET and the POST, as the transfer routes
  already did.
- Claim-path error handling: a duplicate, a filled category or an unpriced distance now
  re-render the offer with the reason instead of a 500 while the offer clock runs; a failure
  to mark the entry promoted is logged loudly rather than failing a completed registration;
  the join form no longer throws when the event is unpublished mid-request; and the claim
  limiter keys on the token rather than a `:slug` that route does not have.

## August 8 — Organiser-defined registration questions

- An organiser can add up to ten of their own questions to the registration form: a short
  answer, a pick from a list, or an extra agreement. Answers appear on the registrants
  export, alongside two new columns for kit size.
- **This is a stated subset of `05-form-builder.md`, not the whole of it.** That spec asks
  for fourteen field types, sections, conditional routing, file upload and profile mapping,
  on the basis of reusing a builder that does not exist in this repository, and its own note
  defers it "until there is evidence that fixed fields are insufficient". The evidence is
  narrow and specific — the spec's own examples of what organisers need to ask (meal option,
  transport, wave, running club) are all a short answer or a pick from a list. Left out on
  purpose, each with a reason in the code: file upload (needs R2 plumbing, size and type
  handling, a retention story), conditional routing (the complexity multiplier, nothing asks
  for it), profile-linked fields, repeating groups and address composites.
- **An answer is stored with its question's label, not just its id.** A question renamed
  after people have answered it would otherwise silently relabel their answers, which is
  worse than useless on an export being used to order 400 meals. The export reads columns
  back through the event's current labels and matches answers by id, so a column means the
  same thing for every row even when the question was renamed halfway through.
- Renaming a question keeps its id, so answers already given stay attached to it.
- **A bulk import is not failed for answers the organiser cannot know.** A required question
  is a question for the participant; demanding it of somebody pasting a spreadsheet would
  have rejected every row.
- An incoherent question is dropped rather than failing the whole event save — a blank label
  removes a question, and a list question with no options is not a question. Losing every
  other edit on a long event form to one bad row would be the wrong trade.
- Asked on every registration path: account, guest, walk-in, waitlist claim and import.
  Validation lives inside `validateGuestForm` so those cannot drift apart.
- One defect caught before it shipped: the save path referenced `formData.rawBody`, which
  does not exist, and would have silently wiped every question on any event save.
- Verified live: a required question was enforced, an option outside the list was refused,
  an import was not blocked, the answer survived a rename with its original label intact,
  and the export column followed the new label. Unit suite 1319/1319.

## August 8 — Registration transfers

- A registration can be handed to somebody else: the holder or the organiser starts it, the
  recipient gets an emailed link, fills in their own details and signs the waiver, and the
  organiser approves before the entry moves.
- **The policy, stated rather than assumed: a transfer moves who is running, and nothing
  else.** It does not move, refund or re-charge any payment. Whatever was paid stays with
  the registration and the two people settle between themselves; any transfer fee an
  organiser wants is arranged out of band. This follows the rule the codebase already has —
  runner-initiated cancellation is a *request* precisely because deciding the refund "is not
  ours to decide", and a transfer that quietly moved money would be making the same call on
  somebody else's bank account. Both the recipient's page and the organiser's page say so.
- **The recipient signs the waiver themselves.** A waiver is a statement about a person's
  own health and risk, so inheriting one would make it worthless — which is the whole reason
  this could not be a name edit. Their emergency contact replaces the previous person's, and
  they choose their own kit size.
- Every credential the previous participant held stops working. The bib number stays with
  the entry — same slot, same start list — but its QR is reissued, so a screenshot the old
  participant kept cannot be scanned in.
- A transferred entry becomes a guest entry unless the recipient already has an account.
  Asserting an identity from an address typed into a form is what the walk-in flow refuses
  to do, for the same reason.
- One live transfer per registration, enforced by a partial unique index: two in flight
  would race to replace the same participant and the loser's recipient would have signed a
  waiver for nothing. Declining is a first-class outcome at both ends, an invite that could
  not be emailed is undone rather than left blocking the registration, and the worker that
  expires waitlist offers now expires stale transfer links too.
- Who it was survives the swap, on the transfer record and in the audit trail. The
  registration itself stops being able to answer that the moment it completes, and it is
  exactly what an organiser asks when two people turn up for one bib.
- Two real defects found while building, both by checking rather than assuming: the guest
  token revoke takes a *purpose* filter rather than a reason string, so the obvious call
  would have revoked nothing at all; and `renderWaiverTemplate` takes `organizerName`, not a
  participant name.
- Verified live end to end on a throwaway event: the participant swapped, the waiver was
  re-signed, the emergency contact was replaced, **every payment field was untouched**, the
  confirmation code survived, old links were revoked and a new one issued, the transfer link
  became single-use, and a second concurrent transfer and a self-transfer were both refused.
  Unit suite 1302/1302.

## August 8 — Per-size race kit inventory

- An event can now stock race kits by size, participants choose a size when they register,
  and the kit table hands over against real stock. Every way into an event records a size:
  account registration, guest, walk-in, a waitlist claim, and bulk import (which learned a
  `size` / `shirt size` column).
- **The count lives in Mongo, not on the Postgres `race_kits` columns.** That table's
  `quantity_available` / `quantity_reserved` pair has never been written by anything except
  the insert that creates the row, so building on it would have meant adopting a counter
  nothing maintains. This mirrors `raceCategories.reserved` instead — a counter already
  proven under an atomic claim.
- **A shirt is claimed when it leaves the table, not when somebody registers.** Reserving at
  registration would be the wrong model: an event routinely registers more people than it
  has shirts and tops up later, and a no-show should not hold one.
- **A live probe caught a real bug before it shipped.** With `stock` at 0, the
  `released: {$exists: false}` branch — which is there so `$inc` can create the counter on
  first use — matched unconditionally, because an absent counter is not less than zero, it
  simply is not there. The first claim on a sold-out size succeeded and handed out a shirt
  that did not exist. Now refused before the update, with a regression test.
- Releasing twice does not take a second shirt: a desk re-scanning somebody is far more
  likely than a genuine second kit. A substitution is recorded rather than hidden, so the
  stock count and what people are actually wearing cannot drift apart. Running out of a size
  answers 409 with a usable message rather than a 500, and the desk can pick another size
  without reloading.
- Editing an event never resets what has been handed over. `released` is not on the form, so
  a plain overwrite would have zeroed every count at the kit table the moment an organiser
  changed anything else about the event.
- A cancelled registration puts its kit back on the books — nothing physically returns, but
  leaving the count down would have the organiser short a shirt on paper that is still in
  the box.
- Verified live: five concurrent claims on three mediums produced exactly three successes,
  a sold-out size was refused, over-returning could not invent stock, and an event edit kept
  the released count intact. Unit suite 1279/1279.

## August 8 — Waitlist

- A full category now offers a waitlist instead of a dead end. Joining asks only for a name,
  email and contact number: the waiver, emergency contact and participation mode are
  collected at promotion, when a slot actually exists, rather than demanded from somebody
  who may never get one.
- **A waitlist entry is not a registration**, which is where this departs from the original
  spec. That said a waitlisted person should be a `Registration` carrying a new `waitlisted`
  status. Measured first: 93 places query registrations and only 4 of them filter on
  `status`, so a new status would have silently added people who are not registered to
  rosters, exports, headcounts, the Postgres shadow, bib assignment and check-in — and
  anything missed fails in the direction of letting someone onto a start line who never got
  a slot. `WaitlistEntry` is a separate collection; nothing that exists today can see one,
  and promotion goes through the ordinary registration paths.
- **An offer holds a real slot**, taken through the same atomic reservation an ordinary
  registration uses. That is what stops two people being promoted into one slot, and stops
  anyone registering past a promoted person while they decide. The cost is that an offer
  must always end, so every path out of `offered` releases the slot, and a new worker
  expires stale offers and passes each freed slot straight to the next in line.
- `createGuestRegistration` gained `skipCapacityReservation`: claiming an offer must not
  reserve a second slot, and the failure paths must not hand back a slot the offer owns.
- A cancellation now offers its freed slot to the next person automatically, backgrounded
  and never able to fail the cancellation itself.
- The offer link is the credential, so only its hash is stored, it is single-use, and an
  expired link and an invented one are answered identically. The offer is bound to one
  email address and cannot be redirected to another.
- The offer email is `locked` in the communication registry — it is time-limited and acts
  on the participant's behalf, so opting out would mean losing a slot without being told it
  was there.
- Verified live on a throwaway event, including the two paths that could oversell: an offer
  held the slot (reserved stayed 1 of 1), claiming it did not take a second, a second offer
  was refused for want of capacity, and expiry released the slot back. Unit suite 1261/1261.

## August 8 — Three guards against repeating this work's mistakes

- **`/healthz` now reports the running commit**, along with the branch and how long the
  process has been up. There was previously no way to ask the app which build it was on,
  and a deploy was reported here as verified on the strength of `/organizer/*` returning
  302 — a mount that answers 302 for any path whether or not the code shipped. Resolved
  once at startup from `RENDER_GIT_COMMIT`, falling back to reading `.git` in development.
- **The tessdata download can no longer fail or hang a deploy.** It fetches from a
  third-party host on every install. It already exited 0 on a failed download, but not on
  an unwritable directory, a cross-filesystem rename, or a stat on a file that vanished —
  and it had no timeout at all, so a host that accepted the connection and never answered
  would hang `npm install` until the build platform gave up. That is a slower and more
  confusing failure than simply not having the file. Verified across four paths: file
  present, unreachable host, host that never answers, unwritable destination — all exit 0.
- **`npm test` no longer reaches production.** There is no staging tier, so a local `.env`
  points at the production MongoDB and Supabase instances; every suite run during the
  onsite work had to be done by hand with that in mind, and care is not a control. Any
  group that is not DB-free unit tests is now refused unless the configured databases are
  local. The rule judges the *target* rather than matching known production hostnames,
  which would fail open the day a new host appears. `ALLOW_REMOTE_TEST_DB=1` overrides it
  explicitly, and the refusal names the host without echoing the password. `test:parallel`
  was spawning the runner directly and would have walked straight past the guard; it now
  goes through the same path, and a test fails if any future script does not.

## August 7 — Registrant list import

- An organiser can upload a participant list as `.csv` or `.xlsx` and have everyone
  entered at once, at `/organizer/events/:eventId/registrants/import`. Preview first,
  write only on confirm, with per-row outcomes — the same shape as the results import.
  It could not have been built before guest registration: most of an imported list has
  no HelloRun account, and there was nowhere to put those people.
- **The sheet reader is now shared with the results import** (`src/utils/spreadsheet-import.js`).
  Both face organisers exporting from tools that agree on nothing, so header matching is
  lenient and unknown columns are ignored rather than rejected. Refactoring it out
  surfaced a difference that mattered: a blank optional column must read as *absent*, not
  as an empty value to format-check, or a blank distance is rejected as "not a positive
  number".
- **Confirmation emails default to off for an import.** A few hundred rows would
  otherwise send a few hundred emails at once, against a daily allowance shared with
  password resets and payment notices.
- **The emergency contact is not waived for an onsite import.** Bulk entry is not a
  reason for nobody to be reachable if a participant gets hurt.
- The waiver records `Imported by organiser (...)` rather than pretending the person
  signed. A spreadsheet cannot capture consent.
- Duplicates are caught twice: within the file, and against existing registrations of
  either kind via the walk-in cross-type guard.
- **A missing category is settled at preview, not at write time.** `raceDistance` is
  required on a registration, and the first live probe passed every row through preview
  as ready and then failed every one of them on write. Now: an event with exactly one
  category fills it in, and any other event rejects the row up front with a message
  saying to add the column. Picking a distance on a participant's behalf is only safe
  when there is nothing to pick.
- **Mobile number is a required column, not just a required field.** The page promised
  three required columns while validation demanded four, so a file without it looked
  acceptable and then failed on every single row.
- Verified end to end against a throwaway event: preview wrote nothing, both rows
  reached Mongo and the Postgres shadow, the email was normalised so a re-import was
  refused, and the probe left nothing behind.

## August 7 — Walk-in registration, and a guest bug it caught

- An organiser can now register someone who turned up on the day, from the check-in
  console. It was the last real race-day gap: no route under `src/routes/organiser/`
  constructed a `Registration` at all. Guest registration removed the blocker, so this
  is mostly assembly over `createGuestRegistration`.
- **The shadow sync is awaited here.** The post-save hook is fire-and-forget and
  `assignBib` throws when the Postgres row is missing — so handing over a bib seconds
  after registering someone was a race, at exactly the moment a desk wants to do it.
  The response reports `readyForBib` either way. A sync failure is not fatal: the
  registration exists and the retry worker catches up.
- **Duplicates are caught across both kinds of registration.** The unique index is
  partial on `userId` being an ObjectId, so it never applies to guests, and the guest
  check only looked at other guests — adding someone who had already registered with an
  account would have created a second, unlinked entry.
- Payment is a checkbox, **default unticked**, and ticking it mirrors the existing
  manual approval convention (`paid` + reviewer + note) rather than inventing a cash
  status. Defaulting off means a rushed desk never records money it did not take.
- An email that already has an account still creates a guest registration; the claim
  flow lets the account holder take it with a verified email, rather than an organiser
  asserting someone's identity from a typed address.
- **Found while probing: the second guest on any event never reached the shadow.**
  `registrations_unique_mongo_event_user_idx` is a plain `UNIQUE (mongo_event_id,
  mongo_user_id)`, and the shadow wrote an empty string for a guest. Postgres treats
  NULLs as distinct but two empty strings collide, so guest #2 onwards silently failed
  to sync — and with that, no check-in and no bib. Now writes `null`. No live guest
  registrations existed yet, so nothing was stranded; two orphaned shadow rows from
  probing were cleaned up.
- Also folded the guest service back onto `getInitialRegistrationPaymentStatus`, which
  it had been duplicating.
- Adds `registrationSource` and `createdByUserId` to `Registration`, Mongo-only — the
  Postgres shadow has an explicit column list and would need a migration for provenance
  nothing downstream reads yet.
- Unit suite 1215/1215.

## August 7 — Claiming a guest registration, and a silently broken audit trail

- A guest registration can now be moved onto an account. Guest registration is
  complete end to end: register without an account, reach it by private link, then
  claim it.
- **Proof of ownership is a verified email**, and nothing weaker would do. The
  registration reference is printed on confirmations and read aloud at desks, and the
  management link can be forwarded — neither is evidence of who you are. An
  unverified account is refused outright, since otherwise registering an address you
  do not control would be enough to take a registration made with it.
- A match makes a registration *claimable*; it never claims it. Each one is confirmed
  explicitly, so nothing is silently folded into an account on the strength of an
  address.
- Claiming revokes the guest links — a forwarded link must not outlive the claim —
  writes an audit event, and saves rather than updating atomically so the post-save
  hook re-syncs the Postgres shadow with the now-present user.
- Refusals are specific: already owned, cancelled, wrong address, unverified,
  restricted account, or an event the account already holds. That last one is flagged
  in the list rather than left to collide with the one-per-account index.
- **Found and fixed: every critical audit write has been failing.** `audit_critical`
  inserts put an explicit column list before `${sql(rows, ...columns)}`, which made
  postgres.js fall through to its *select* builder and try to escape each row object
  as a column name — `str.replace is not a function`. Because the callers run in the
  background, the throw was only ever logged. Payment approvals, submission reviews,
  cancellations and staff changes were going unrecorded. Verified fixed, including
  idempotency on repeat writes.
- Unit suite 1204/1204.

## August 7 — Guest registration, and the switch that makes it reachable

- Guests can now register without a HelloRun account, reach their registration
  through a private link, and see what they are giving up by not having an account.
  Off per event unless an organiser enables it.
- Kept as its own service rather than folded into the account flow. That flow starts
  from a signed-in user and reads their profile, workspace and prior registrations;
  threading "maybe there is no user" through it would put a null check in front of
  every one of those reads — the same shape as the bug that made `/events/:slug`
  return 500 for signed-out visitors.
- The link is the credential, so only its hash is stored, it is shown exactly once,
  and it is **rendered rather than redirected to** — a token in a URL lands in browser
  history, referrer headers and server logs. Every failed lookup returns one identical
  message, because distinguishing "expired" from "unknown" tells a visitor that
  somebody's registration exists. The registration reference never grants access; it
  is printed on confirmations and read aloud at desks.
- Duplicates are refused on email. Accounts get that from a unique index; guests
  cannot, since that index keys on a user they do not have. It is a check, not a
  guarantee, and says so.
- **Added the organiser toggle.** Without it the setting existed but nothing could turn
  it on — verified in production that 0 events had it enabled — so the entire flow was
  unreachable. Wired through all four points of the event form (new-form default,
  body parsing, read-back when editing, persistence), with the hidden-field fallback
  so unchecking sticks. Verified the full round trip, including turning it back off.
- The public event page links to the guest form only when the setting is on *and*
  registration is actually open, so nobody is walked into a refusal.
- Claiming a guest registration into an account is still to come.
- Unit suite 1192/1192.

## August 7 — Migration 022 was the root of the whole shadow collapse

- Chasing the submission shadow led to a single cause. `022_step_competition_events.sql`
  adds `challenge_metrics`, `primary_challenge_metric` and `target_steps` to
  `events_core`, and the event shadow writes all three. With `022` unapplied those
  columns did not exist, so **every event sync failed**, which then failed every
  submission sync with "Event not found", and left onsite check-in unable to resolve
  an event at all.
- `022` had never applied because its `CREATE OR REPLACE VIEW` tried to reorder an
  existing view's columns — fixed earlier with a `DROP VIEW IF EXISTS`. Applying it was
  previously deferred on the grounds that it is gated behind its own backfill and smoke
  tests; that was right in isolation and wrong in context, because leaving it unapplied
  was actively breaking three subsystems.
- Pre-flighted read-only first: no existing row violated any new CHECK constraint, the
  replaced view had no dependents, and every added column carries a default. Applied.
  `FEATURE_STEP_COMPETITIONS_ENABLED` is unchanged and still off — the schema and the
  feature flag are separate things.
- Then re-ran the blocked backfills. Events **353/353** (was 0). Submissions 0 → 75.
- **Onsite check-in now resolves 60 of 108 registrations, up from 0.**
- What remains cannot be repaired: the other 48 onsite registrations point at events
  hard-deleted from Mongo, and of 1,209 distinct submission runners only 79 still exist.
  The residual 1,136 submission failures are 716 deleted users and 417 deleted events.
  Orphaned historical data, not a sync fault.
- **Correction to the previous entry**, which claimed all 108 onsite registrations
  resolved after the registration backfill. The registrations table was repaired, but
  `recordCheckIn` resolves `events_core` first and that was still empty — the
  verification checked the wrong table.

## August 7 — Foundation for guest registration

- Groundwork only: a registration can now *represent* someone without a HelloRun
  account. The guest flow itself is not built, and nothing user-facing changed.
- `Registration.userId` is required for an account registration and optional for a
  guest, keyed off a new `participantType` defaulting to `account`. Relaxing the
  field outright would have let a missing user slip through silently in the 46 code
  paths that assume one; this keeps the invariant exactly where it was.
- The unique index on `{eventId, userId}` is replaced by a **partial** one, so guest
  rows do not all collide on a single null. It is named explicitly, because Mongoose
  derives the old index's own name from that key and `autoIndex` is on — declaring
  both under one name would fail index creation at boot.
- Dropping the old index is a separate script that **refuses to run until the
  replacement exists**, since dropping first would leave nothing enforcing one
  registration per account. Both enforce the same rule meanwhile, so the overlap is
  harmless. Verified: it correctly refuses today.
- Migration `024` relaxes `runner_user_id` on the three onsite tables and
  `mongo_user_id` on the shadow. Additive only — existing rows keep their values, the
  columns stay foreign keys, and nothing that writes a user stops doing so. Applied.
- Audited the 46 paths first. They cluster in submissions, payments, badges,
  certificates and shop — flows a guest cannot enter — and the organiser-facing ones
  already guard a missing user (`runner?.email`, `registration?.userId?.email`),
  while the registrant list renders from the participant snapshot rather than the
  user. That is what makes the feature viable without a broad refactor.
- Unit suite 1163/1163.

## August 7 — Repair the Postgres shadow, which onsite check-in depends on

- Found while sizing guest registration: **0 of 108 onsite registrations existed in
  the Postgres shadow**, so the check-in console shipped earlier could not resolve a
  single real participant. It reported them honestly as "Not synced" rather than
  failing, but the feature was inert on live data.
- Root cause was a cascade. The shadow resolves a registration through its user, and
  264 of 599 users had never synced; 420 sync failures were logged, 411 of them
  submissions, all reading "App user not found".

## August 7 — Bib QR codes can be withdrawn

- The encoded token already proved a code came from us and had not been altered,
  but a purely stateless token stays valid for as long as the key does. Cancelling
  a registration or reissuing a bib now makes the old code stop working.
- What is stored is the token *identity*, not the token. Holding the identity gets
  you nothing — a usable code also needs the encryption key, which never leaves
  the server. Keeping the identity readable is what allows the same identity to be
  re-encrypted on demand, which matters because **the race pass regenerates its
  image on every page load**: minting a fresh identity per view would kill a
  runner's screenshot the moment they reopened the page. Each render differs
  (random IV) while resolving to the same identity.
- Scanning now separates `revoked` and `unknown` from `invalid`, so staff are told
  "this was withdrawn" rather than "this is not a bib". Codes printed before
  revocation existed carry no identity; they are accepted and flagged rather than
  refused, since refusing would invalidate everything already in circulation.
- Revocation fires on registration cancellation and on bib reassignment — without
  the latter, a reissued bib would leave the previous holder's printed QR able to
  check somebody in. One live code per bib, with the unique index partial on
  `revokedAt` so a bib can be reissued after revoking.
- Verified end to end against the database: stable identity across renders, wrong
  event refused, revoked screenshot refused, reissue works, a well-formed but
  never-issued identity refused, pre-revocation codes still scanning.
- No migration: a new Mongo collection needs none.
- Unit suite 1150/1150; onsite integration suite still 15/15.

## August 7 — Race-category capacity is now actually atomic

- Closed a real correctness bug on the registration path. The check counted
  confirmed registrations and then inserted, so two people submitting for the
  last slot both read the same count and both got in. Counting is not a
  reservation, however close to the insert it happens.
- A slot is now taken with a single atomic document update: the `slots` bound is
  part of the update filter and the increment happens in the same operation, so a
  slot is either claimed by exactly one caller or the update matches nothing.
  Proven against the live driver — 20 simultaneous attempts at 3 slots produced
  exactly 3 reservations and 17 refusals.
- Every path that can hold a slot and then fail gives it back, including the
  duplicate-key race, and cancelling releases explicitly (the old count-based
  check did that implicitly by no longer counting the row). Release is floored at
  zero so a double release cannot invent capacity.
- `reserved` has no schema default on purpose: an absent value means "never
  tracked" and reads as zero, so categories predating the counter keep working.
  `backfill-category-reservations.js` seeds it from reality, recounting rather
  than adjusting so it is safe to re-run and usable later to repair drift.
- **Zero production exposure at the time of the fix** — no event currently uses a
  category slot limit, confirmed before changing anything, which is why this was
  the right moment to do it. The backfill dry run was a no-op.
- Unit suite 1138/1138.

## August 7 — Results import from a spreadsheet

- Organisers can import results from a `.csv` or `.xlsx`. Most of this already
  existed and was unreachable: `result-import-validation.service.js` had full row

  `Registration.userId` is `required: true` and a genuine walk-in has no account,

  account-holder variant could ship today, which would be a confusing feature, so

## August 7 — Race pass, bib scanning, and registration cancellation

- **Runners can see their own bib and check-in code.** New race pass at
  `/my-registrations/:registrationId/race-pass`, scoped to the signed-in runner
  so one pass cannot be read from another. Onsite entries link to it from the
  registrations list; virtual ones do not. Previously the QR endpoints were
  organiser-only, so the scanning half of race day had nothing to scan.
- **The bib QR no longer leaks database ids.** It carried
  `EVENT:{mongoId}|BIB:{n}|TIME:{ts}` in plaintext, so anyone who photographed a
  bib learned a live event id and nothing stopped them editing it into another
  bib. It now carries an opaque AES-256-GCM token that reveals nothing and fails
  closed if altered. `token-encryption.service.js` gained purpose-scoped key
  derivation rather than a second crypto envelope; Strava keeps its own key and
  call signature. Codes printed before the change still scan — `resolveScannedQr`
  accepts both and reports which it saw. Revocation still needs a token store and
  remains queued behind migration `023`.
- **Bib scanning** via `POST /organizer/events/:eventId/check-in/scan`, answering
  the cases staff hit at a start line with typed outcomes: `checked_in`,
  `already_checked_in`, `cancelled`, `wrong_event`, `unknown_bib`, `invalid`.
  Payment is a warning rather than a refusal — many events settle at the desk.
  Bib lookup for scanning is an exact match, deliberately separate from the
  roster's partial search: resolving "10" to bib "101" would check in the wrong
  runner. Scanning uses the browser's `BarcodeDetector`; browsers without it
  (Safari today) get manual code entry rather than a broken camera panel.
- **Registration cancellation.** `cancelled`/`refunded` were valid statuses that
  nothing ever set. Cancelling now frees the category slot, voids the bib so the
  number can be reissued, stops any check-in counting, records who/when/why with
  an audit event, and notifies the runner through a new `registration.cancelled`
  communication event. Offered only for live registrations, behind the shared
  high-risk confirmation. Runner-initiated cancellation needs an
  organiser-configurable policy and is not included.
- Unit suite 1102/1102.

## August 7 — Onsite results now reach rankings, leaderboards, and certificates

- Closed the onsite finisher dead end. An approved onsite result previously awarded a
  badge and nothing else: `ranking.service.js` requires `mongo_submission_id`,
  `leaderboard.service.js` queries the Mongo `Submission` collection, and no
