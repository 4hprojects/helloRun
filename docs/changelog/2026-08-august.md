# HelloRun Changelog — August 2026

## August 7 — Registrant list import

- An organiser can upload a participant list as `.csv` or `.xlsx` and have everyone
  entered at once, at `/organizer/events/:eventId/registrants/import`. Preview first,
  write only on confirm, with per-row outcomes — the same shape as the results import.
  It could not have been built before guest registration: most of an imported list has
  no HelloRun account, and there was nowhere to put those people.
- **The sheet reader is now shared with the results import** (`src/utils/spreadsheet-import.js`).
  Both face organisers exporting from tools that agree on nothing, so header matching is
  lenient and unknown columns are ignored rather than rejected. Refactoring it out
  surfaced a difference that mattered: a blank optional column must read as *absent*, not
  as an empty value to format-check, or a blank distance is rejected as "not a positive
  number".
- **Confirmation emails default to off for an import.** A few hundred rows would
  otherwise send a few hundred emails at once, against a daily allowance shared with
  password resets and payment notices.
- **The emergency contact is not waived for an onsite import.** Bulk entry is not a
  reason for nobody to be reachable if a participant gets hurt.
- The waiver records `Imported by organiser (...)` rather than pretending the person
  signed. A spreadsheet cannot capture consent.
- Duplicates are caught twice: within the file, and against existing registrations of
  either kind via the walk-in cross-type guard.
- **A missing category is settled at preview, not at write time.** `raceDistance` is
  required on a registration, and the first live probe passed every row through preview
  as ready and then failed every one of them on write. Now: an event with exactly one
  category fills it in, and any other event rejects the row up front with a message
  saying to add the column. Picking a distance on a participant's behalf is only safe
  when there is nothing to pick.
- **Mobile number is a required column, not just a required field.** The page promised
  three required columns while validation demanded four, so a file without it looked
  acceptable and then failed on every single row.
- Verified end to end against a throwaway event: preview wrote nothing, both rows
  reached Mongo and the Postgres shadow, the email was normalised so a re-import was
  refused, and the probe left nothing behind.

## August 7 — Walk-in registration, and a guest bug it caught

- An organiser can now register someone who turned up on the day, from the check-in
  console. It was the last real race-day gap: no route under `src/routes/organiser/`
  constructed a `Registration` at all. Guest registration removed the blocker, so this
  is mostly assembly over `createGuestRegistration`.
- **The shadow sync is awaited here.** The post-save hook is fire-and-forget and
  `assignBib` throws when the Postgres row is missing — so handing over a bib seconds
  after registering someone was a race, at exactly the moment a desk wants to do it.
  The response reports `readyForBib` either way. A sync failure is not fatal: the
  registration exists and the retry worker catches up.
- **Duplicates are caught across both kinds of registration.** The unique index is
  partial on `userId` being an ObjectId, so it never applies to guests, and the guest
  check only looked at other guests — adding someone who had already registered with an
  account would have created a second, unlinked entry.
- Payment is a checkbox, **default unticked**, and ticking it mirrors the existing
  manual approval convention (`paid` + reviewer + note) rather than inventing a cash
  status. Defaulting off means a rushed desk never records money it did not take.
- An email that already has an account still creates a guest registration; the claim
  flow lets the account holder take it with a verified email, rather than an organiser
  asserting someone's identity from a typed address.
- **Found while probing: the second guest on any event never reached the shadow.**
  `registrations_unique_mongo_event_user_idx` is a plain `UNIQUE (mongo_event_id,
  mongo_user_id)`, and the shadow wrote an empty string for a guest. Postgres treats
  NULLs as distinct but two empty strings collide, so guest #2 onwards silently failed
  to sync — and with that, no check-in and no bib. Now writes `null`. No live guest
  registrations existed yet, so nothing was stranded; two orphaned shadow rows from
  probing were cleaned up.
- Also folded the guest service back onto `getInitialRegistrationPaymentStatus`, which
  it had been duplicating.
- Adds `registrationSource` and `createdByUserId` to `Registration`, Mongo-only — the
  Postgres shadow has an explicit column list and would need a migration for provenance
  nothing downstream reads yet.
- Unit suite 1215/1215.

## August 7 — Claiming a guest registration, and a silently broken audit trail

- A guest registration can now be moved onto an account. Guest registration is
  complete end to end: register without an account, reach it by private link, then
  claim it.
- **Proof of ownership is a verified email**, and nothing weaker would do. The
  registration reference is printed on confirmations and read aloud at desks, and the
  management link can be forwarded — neither is evidence of who you are. An
  unverified account is refused outright, since otherwise registering an address you
  do not control would be enough to take a registration made with it.
- A match makes a registration *claimable*; it never claims it. Each one is confirmed
  explicitly, so nothing is silently folded into an account on the strength of an
  address.
- Claiming revokes the guest links — a forwarded link must not outlive the claim —
  writes an audit event, and saves rather than updating atomically so the post-save
  hook re-syncs the Postgres shadow with the now-present user.
- Refusals are specific: already owned, cancelled, wrong address, unverified,
  restricted account, or an event the account already holds. That last one is flagged
  in the list rather than left to collide with the one-per-account index.
- **Found and fixed: every critical audit write has been failing.** `audit_critical`
  inserts put an explicit column list before `${sql(rows, ...columns)}`, which made
  postgres.js fall through to its *select* builder and try to escape each row object
  as a column name — `str.replace is not a function`. Because the callers run in the
  background, the throw was only ever logged. Payment approvals, submission reviews,
  cancellations and staff changes were going unrecorded. Verified fixed, including
  idempotency on repeat writes.
- Unit suite 1204/1204.

## August 7 — Guest registration, and the switch that makes it reachable

- Guests can now register without a HelloRun account, reach their registration
  through a private link, and see what they are giving up by not having an account.
  Off per event unless an organiser enables it.
- Kept as its own service rather than folded into the account flow. That flow starts
  from a signed-in user and reads their profile, workspace and prior registrations;
  threading "maybe there is no user" through it would put a null check in front of
  every one of those reads — the same shape as the bug that made `/events/:slug`
  return 500 for signed-out visitors.
- The link is the credential, so only its hash is stored, it is shown exactly once,
  and it is **rendered rather than redirected to** — a token in a URL lands in browser
  history, referrer headers and server logs. Every failed lookup returns one identical
  message, because distinguishing "expired" from "unknown" tells a visitor that
  somebody's registration exists. The registration reference never grants access; it
  is printed on confirmations and read aloud at desks.
- Duplicates are refused on email. Accounts get that from a unique index; guests
  cannot, since that index keys on a user they do not have. It is a check, not a
  guarantee, and says so.
- **Added the organiser toggle.** Without it the setting existed but nothing could turn
  it on — verified in production that 0 events had it enabled — so the entire flow was
  unreachable. Wired through all four points of the event form (new-form default,
  body parsing, read-back when editing, persistence), with the hidden-field fallback
  so unchecking sticks. Verified the full round trip, including turning it back off.
- The public event page links to the guest form only when the setting is on *and*
  registration is actually open, so nobody is walked into a refusal.
- Claiming a guest registration into an account is still to come.
- Unit suite 1192/1192.

## August 7 — Migration 022 was the root of the whole shadow collapse

- Chasing the submission shadow led to a single cause. `022_step_competition_events.sql`
  adds `challenge_metrics`, `primary_challenge_metric` and `target_steps` to
  `events_core`, and the event shadow writes all three. With `022` unapplied those
  columns did not exist, so **every event sync failed**, which then failed every
  submission sync with "Event not found", and left onsite check-in unable to resolve
  an event at all.
- `022` had never applied because its `CREATE OR REPLACE VIEW` tried to reorder an
  existing view's columns — fixed earlier with a `DROP VIEW IF EXISTS`. Applying it was
  previously deferred on the grounds that it is gated behind its own backfill and smoke
  tests; that was right in isolation and wrong in context, because leaving it unapplied
  was actively breaking three subsystems.
- Pre-flighted read-only first: no existing row violated any new CHECK constraint, the
  replaced view had no dependents, and every added column carries a default. Applied.
  `FEATURE_STEP_COMPETITIONS_ENABLED` is unchanged and still off — the schema and the
  feature flag are separate things.
- Then re-ran the blocked backfills. Events **353/353** (was 0). Submissions 0 → 75.
- **Onsite check-in now resolves 60 of 108 registrations, up from 0.**
- What remains cannot be repaired: the other 48 onsite registrations point at events
  hard-deleted from Mongo, and of 1,209 distinct submission runners only 79 still exist.
  The residual 1,136 submission failures are 716 deleted users and 417 deleted events.
  Orphaned historical data, not a sync fault.
- **Correction to the previous entry**, which claimed all 108 onsite registrations
  resolved after the registration backfill. The registrations table was repaired, but
  `recordCheckIn` resolves `events_core` first and that was still empty — the
  verification checked the wrong table.

## August 7 — Foundation for guest registration

- Groundwork only: a registration can now *represent* someone without a HelloRun
  account. The guest flow itself is not built, and nothing user-facing changed.
- `Registration.userId` is required for an account registration and optional for a
  guest, keyed off a new `participantType` defaulting to `account`. Relaxing the
  field outright would have let a missing user slip through silently in the 46 code
  paths that assume one; this keeps the invariant exactly where it was.
- The unique index on `{eventId, userId}` is replaced by a **partial** one, so guest
  rows do not all collide on a single null. It is named explicitly, because Mongoose
  derives the old index's own name from that key and `autoIndex` is on — declaring
  both under one name would fail index creation at boot.
- Dropping the old index is a separate script that **refuses to run until the
  replacement exists**, since dropping first would leave nothing enforcing one
  registration per account. Both enforce the same rule meanwhile, so the overlap is
  harmless. Verified: it correctly refuses today.
- Migration `024` relaxes `runner_user_id` on the three onsite tables and
  `mongo_user_id` on the shadow. Additive only — existing rows keep their values, the
  columns stay foreign keys, and nothing that writes a user stops doing so. Applied.
- Audited the 46 paths first. They cluster in submissions, payments, badges,
  certificates and shop — flows a guest cannot enter — and the organiser-facing ones
  already guard a missing user (`runner?.email`, `registration?.userId?.email`),
  while the registrant list renders from the participant snapshot rather than the
  user. That is what makes the feature viable without a broad refactor.
- Unit suite 1163/1163.

## August 7 — Repair the Postgres shadow, which onsite check-in depends on

- Found while sizing guest registration: **0 of 108 onsite registrations existed in
  the Postgres shadow**, so the check-in console shipped earlier could not resolve a
  single real participant. It reported them honestly as "Not synced" rather than
  failing, but the feature was inert on live data.
- Root cause was a cascade. The shadow resolves a registration through its user, and
  264 of 599 users had never synced; 420 sync failures were logged, 411 of them
  submissions, all reading "App user not found".
- Ran the existing `backfill-app-users` and `backfill-registration-payment-shadow`
  scripts. Users: 599/599. Registrations: 3,070 processed, 1,957 synced, 0 failed.
  **All 108 onsite registrations now resolve.**
- Fixed a defect that stopped the registration backfill completing at all: it held a
  single `.cursor()` over the whole collection, which the server reaped mid-run
  ("cursor id not found"), leaving the shadow half-populated. It now pages by `_id`,
  so every query is short, and skips records already in the shadow so an interrupted
  run resumes instead of restarting — the first rerun burned its whole budget
  re-syncing the same 1,611 rows without reaching new ones.
- Two counts look odd and are not errors: `app_users` (931) and shadow registrations
  (3,568) exceed their Mongo counts (599 and 3,070) because the shadow retains rows
  for records since deleted from Mongo. Verified no duplicate `mongo_user_id` or
  email in `app_users`.
- Of the 108 onsite registrations, only 10 belong to a user that still exists in
  Mongo; the other 98 are orphaned by earlier user deletions. They sync, but there is
  no runner behind them.

## August 7 — Fix two communication events that could never send

- `organiser.runner_contact` and `organiser.direct_message` both declared
  `emailEnabled: true` but had no branch in `sendEventEmail`, which throws
  "No email sender registered" for an unknown key. `notify()` caught that and
  recorded a failed send.
- The public contact-organiser flow checks `result?.email?.status !== 'sent'`, so
  **every runner who messaged an organiser was shown an error and the message
  never arrived.** Organiser-to-runner messages fell back to in-app only.
- Both now have senders, and both set `reply_to` — which is the point of a relay:
  the organiser replies to the runner and vice versa, rather than to HelloRun.
  `reply_to` support did not exist in the email service before this.
- The relayed text is written by one user and read by another, so it is escaped;
  newlines are converted afterwards so escaping does not cost the message its
  shape. Verified that a `<script>` tag and an `onerror` image payload do not
  survive.
- Added a test that fails if any registered communication event lacks a sender, so
  this class of bug cannot return silently. It has now bitten three times in this
  work.
- Unit suite 1155/1155.

## August 7 — Bib QR codes can be withdrawn

- The encoded token already proved a code came from us and had not been altered,
  but a purely stateless token stays valid for as long as the key does. Cancelling
  a registration or reissuing a bib now makes the old code stop working.
- What is stored is the token *identity*, not the token. Holding the identity gets
  you nothing — a usable code also needs the encryption key, which never leaves
  the server. Keeping the identity readable is what allows the same identity to be
  re-encrypted on demand, which matters because **the race pass regenerates its
  image on every page load**: minting a fresh identity per view would kill a
  runner's screenshot the moment they reopened the page. Each render differs
  (random IV) while resolving to the same identity.
- Scanning now separates `revoked` and `unknown` from `invalid`, so staff are told
  "this was withdrawn" rather than "this is not a bib". Codes printed before
  revocation existed carry no identity; they are accepted and flagged rather than
  refused, since refusing would invalidate everything already in circulation.
- Revocation fires on registration cancellation and on bib reassignment — without
  the latter, a reissued bib would leave the previous holder's printed QR able to
  check somebody in. One live code per bib, with the unique index partial on
  `revokedAt` so a bib can be reissued after revoking.
- Verified end to end against the database: stable identity across renders, wrong
  event refused, revoked screenshot refused, reissue works, a well-formed but
  never-issued identity refused, pre-revocation codes still scanning.
- No migration: a new Mongo collection needs none.
- Unit suite 1150/1150; onsite integration suite still 15/15.

## August 7 — Race-category capacity is now actually atomic

- Closed a real correctness bug on the registration path. The check counted
  confirmed registrations and then inserted, so two people submitting for the
  last slot both read the same count and both got in. Counting is not a
  reservation, however close to the insert it happens.
- A slot is now taken with a single atomic document update: the `slots` bound is
  part of the update filter and the increment happens in the same operation, so a
  slot is either claimed by exactly one caller or the update matches nothing.
  Proven against the live driver — 20 simultaneous attempts at 3 slots produced
  exactly 3 reservations and 17 refusals.
- Every path that can hold a slot and then fail gives it back, including the
  duplicate-key race, and cancelling releases explicitly (the old count-based
  check did that implicitly by no longer counting the row). Release is floored at
  zero so a double release cannot invent capacity.
- `reserved` has no schema default on purpose: an absent value means "never
  tracked" and reads as zero, so categories predating the counter keep working.
  `backfill-category-reservations.js` seeds it from reality, recounting rather
  than adjusting so it is safe to re-run and usable later to repair drift.
- **Zero production exposure at the time of the fix** — no event currently uses a
  category slot limit, confirmed before changing anything, which is why this was
  the right moment to do it. The backfill dry run was a no-op.
- Unit suite 1138/1138.

## August 7 — Runners can ask to cancel

- A runner can now ask to cancel a registration from their registrations page.
  It records the ask and tells the organiser; it does **not** cancel.
- That split is deliberate. Cancelling a paid registration decides what happens
  to the money, and that is the organiser's call — not something to infer from a
  runner tapping a button. The runner-facing copy says plainly that nothing is
  cancelled and no refund is issued automatically; the organiser's roster shows
  the request with "Nothing is cancelled until you do it below, including
  anything owed back", right beside the existing cancel action.
- Requests are refused when the registration is not live, and cannot be repeated.
  The lookup is scoped to the signed-in runner, so one runner cannot request
  against another's registration.
- Added a `registration.cancellation_requested` communication event **with its
  email sender wired**, having hit exactly that gap on the previous event.
- No migration: the two new Registration fields are optional.
- Unit suite 1127/1127.

## August 7 — Race-day staff can be delegated per event

- Until now, checking runners in required the organiser's own login on the
  organiser's own phone. An event can now have assigned staff with named
  permissions: `check_in` (check-in, scanning, bibs), `race_kit`, and `results`.
- Deliberately **not** a new value on `User.role`. That field is global and
  checked in dozens of places; widening it would grant something everywhere to
  solve a problem that exists on one event. `EventStaff` scopes a grant to a
  single event, and revoking is one write.
- `requireOnsiteEventAccess(permission)` is a sibling of
  `requireOrganizerEventAccess`, not an edit to it: the original rejects anyone
  who is not an organiser or admin before any per-event check runs, and race-day
  volunteers are ordinary runner accounts. Widening the original would have
  loosened every route using it.
- Staff reach only the onsite routes wrapped in the new guard, each asking for the
  permission its job needs. The staff-management screens stay organiser/admin
  only, so staff can never grant access to themselves or anyone else.
- Permissions are an allowlist, so a crafted form post cannot invent one.
  Revoking keeps the row, leaving who-had-access-when answerable after the event;
  re-adding someone previously removed reinstates them rather than colliding with
  the unique index. Granting requires an existing account — this grants access, it
  does not create accounts.
- No migration: a new Mongo collection needs none, and `User.role` is untouched.
- Unit suite 1122/1122.

## August 7 — Results import from a spreadsheet

- Organisers can import results from a `.csv` or `.xlsx`. Most of this already
  existed and was unreachable: `result-import-validation.service.js` had full row
  validation, error categorisation and error-CSV generation but was imported by
  nothing, and `webhooks/timing-system.js` held the only row-processing logic,
  behind a signature-gated machine endpoint. `exceljs` already reads both
  formats, so no parser package was added.
- Preview then commit — the file is parsed and validated with nothing written,
  and only rows that passed are offered. Header matching is lenient because
  timing exports disagree wildly ("Bib No", "RACE NUMBER", "Chip Time", "Gun
  Time" all resolve); unknown columns are ignored and blank spacer rows skipped
  rather than reported as errors. Rejected rows download as a CSV.
- Imported results land as **submitted**, never auto-approved: approving is what
  places a runner on the leaderboard, so it stays deliberate. Rows apply
  independently, so one unknown bib cannot discard a field's worth of results.
  Capped at 2000 rows with truncation reported rather than silent.
- **Walk-in registration was skipped, not forgotten.** It is not code-only:
  `Registration.userId` is `required: true` and a genuine walk-in has no account,
  so it is blocked by the same constraint as guest registration. Only an
  account-holder variant could ship today, which would be a confusing feature, so
  it waits for the guest work.
- Unit suite 1111/1111.

## August 7 — Race pass, bib scanning, and registration cancellation

- **Runners can see their own bib and check-in code.** New race pass at
  `/my-registrations/:registrationId/race-pass`, scoped to the signed-in runner
  so one pass cannot be read from another. Onsite entries link to it from the
  registrations list; virtual ones do not. Previously the QR endpoints were
  organiser-only, so the scanning half of race day had nothing to scan.
- **The bib QR no longer leaks database ids.** It carried
  `EVENT:{mongoId}|BIB:{n}|TIME:{ts}` in plaintext, so anyone who photographed a
  bib learned a live event id and nothing stopped them editing it into another
  bib. It now carries an opaque AES-256-GCM token that reveals nothing and fails
  closed if altered. `token-encryption.service.js` gained purpose-scoped key
  derivation rather than a second crypto envelope; Strava keeps its own key and
  call signature. Codes printed before the change still scan — `resolveScannedQr`
  accepts both and reports which it saw. Revocation still needs a token store and
  remains queued behind migration `023`.
- **Bib scanning** via `POST /organizer/events/:eventId/check-in/scan`, answering
  the cases staff hit at a start line with typed outcomes: `checked_in`,
  `already_checked_in`, `cancelled`, `wrong_event`, `unknown_bib`, `invalid`.
  Payment is a warning rather than a refusal — many events settle at the desk.
  Bib lookup for scanning is an exact match, deliberately separate from the
  roster's partial search: resolving "10" to bib "101" would check in the wrong
  runner. Scanning uses the browser's `BarcodeDetector`; browsers without it
  (Safari today) get manual code entry rather than a broken camera panel.
- **Registration cancellation.** `cancelled`/`refunded` were valid statuses that
  nothing ever set. Cancelling now frees the category slot, voids the bib so the
  number can be reissued, stops any check-in counting, records who/when/why with
  an audit event, and notifies the runner through a new `registration.cancelled`
  communication event. Offered only for live registrations, behind the shared
  high-risk confirmation. Runner-initiated cancellation needs an
  organiser-configurable policy and is not included.
- Unit suite 1102/1102.

## August 7 — Onsite results now reach rankings, leaderboards, and certificates

- Closed the onsite finisher dead end. An approved onsite result previously awarded a
  badge and nothing else: `ranking.service.js` requires `mongo_submission_id`,
  `leaderboard.service.js` queries the Mongo `Submission` collection, and no
  certificate path was onsite-aware — and onsite results created no Submission.
- An approved onsite result is now materialised as an approved `Submission` via
  `onsite-result-submission.service.js`, so every existing consumer works unchanged.
  **No schema change was needed**: `Submission.participationMode` already carried
  `'onsite'` and `leaderboard.service.js` already filtered on it — it was waiting for
  rows that never arrived. The alternative, teaching ranking, leaderboard and
  certificate code to read `onsite_results` directly, would have forked three services
  and left every future consumer to remember both sources.
- Extracted `applyApprovedSubmissionEffects` in `submission.service.js` — leaderboard
  cache, certificate, notification, achievements, milestones and ranking sync — and
  used it for both virtual review and onsite approval, so the two cannot drift.
- Distance is resolved from the recorded result, then the race category, then the
  registration's distance label. When none of them knows, approval reports that the
  result did not enter the results rather than inventing a distance that would feed a
  ranking. Signed labels such as `-5K` are refused instead of parsing as 5.
- Marshal-recorded finishes store `proofType: 'manual'` with a plain note rather than
  fabricated proof metadata. Re-approving updates the existing submission, which the
  unique `registrationId` index already enforced.
- Materialisation failures are surfaced, not swallowed: the Postgres approval is
  already committed by then, so the endpoint returns `submissionCreated` plus a reason
  and the results page shows it, instead of implying a finisher is ranked.
- Guest registrations are explicitly rejected here with a clear message — they have no
  runner to rank. Relevant once guest registration exists.
- Unit suite 1084/1084.

## August 7 — Live check-in board, onsite results UI, and real Phase 7 test coverage

- Added the live check-in board (`/organizer/events/:eventId/check-in/board`). The
  entire realtime API already existed and was unreachable. First paint is
  server-rendered and the page then polls, so a dropped connection leaves the
  last known figures on screen with a staleness notice rather than blanking.
- Fixed a **broken query** that made the dashboard endpoints 500:
  `getCheckInVelocity` used `INTERVAL '${windowMinutes} minutes'`, which places a
  bound parameter inside a string literal — Postgres received
  `INTERVAL '$1 minutes'` and rejected it. Now uses `make_interval(mins => ...)`.
- Fixed a fabricated estimate: `estimateCheckInCompletion` defaulted the recent
  check-in count to 1 when there were none, producing a confident completion time
  out of nothing. It now reports no estimate when there is no basis for one.
  Realtime totals are also scoped to onsite registrations so the board agrees
  with the check-in console.
- Added the onsite results page (`/organizer/events/:eventId/onsite-results`) for
  recording finish times and approving results. Finish times are validated and
  converted to milliseconds server-side, which wires up
  `result-import-validation.service.js` — 258 lines that were imported by nothing.
  The page states plainly that approval currently awards badges only and does not
  yet reach the leaderboard or certificates.
- Fixed `decodeQRData`, which returned `success: true` for any input that did not
  throw — `'garbage'` decoded "successfully" with undefined ids and a `NaN`
  timestamp. It now requires EVENT, BIB and a numeric TIME, and splits on the
  first colon so values containing one survive.
- **Deleted `tests/phase7-extended.unit.test.js` and
  `phase7-extended-fixed.unit.test.js`** — 621 lines that imported zero
  application code, building mock objects and asserting on the mocks. They
  contributed ~30 passing tests while providing no regression protection, in the
  exact area being extended. Both bugs above were sitting under that coverage.
  Replaced with `tests/onsite-result-validation.unit.test.js`, which exercises the
  real validator and QR helpers.
- Linked the onsite pages from the organiser event-details tools grid, gated on
  `supportsOnsiteOperations`, so they are no longer reachable only by direct URL.
- Unit suite 1074/1074 (net change reflects removing the placebo tests).

## August 7 — Organizer race-day check-in console; onsite uniqueness fixes

- Reviewed the proposed onsite implementation pack and found its premise out of
  date: onsite events already ship (`Event.eventType` `virtual|onsite|hybrid`,
  `Registration.participationMode`, bibs, check-ins, race kits, result imports,
  QR generation, timing webhook). Filed the review and moved the pack to

  live onsite endpoints.
- Fixed two correctness defects in the Phase 7 onsite tables via additive
  migration `023_onsite_checkin_bib_uniqueness.sql`: `check_ins` had no
  uniqueness on `(event_core_id, registration_id)`, so a repeated scan inserted a
  second row and inflated `v_event_checkin_summary`; and `assignBib`'s
  `ON CONFLICT (mongo_bib_assignment_id)` never fired (the INSERT omits that
  column, and Postgres does not treat NULLs as conflicting), so a registration
  could accumulate multiple live bibs. The migration reconciles existing
  duplicates first, keeping the earliest row and voiding surplus bibs.
- `recordCheckIn` now upserts and reports `was_already_checked_in`, preserving
  the original arrival time; `assignBib` targets the new live-bib partial index

## August 6 — Public event-details 500 for signed-out visitors (fix verification + regression coverage)

- Diagnosed a production `HTTP 500` on `GET /events/:slug` affecting every
  signed-out visitor to every event. Root cause: `isOwnOrganizerEvent(user = {},
  ...)` in `src/utils/workspace.js` used a default parameter (applies only to
  `undefined`), so a guest's `res.locals.user === null` reached `user.role` and
  threw; the throw was caught in `getEventDetails` and rendered as the generic
  500 page.
- The code fix already shipped in commit `b70b50d` (`const safeUser = user ||
  {}`); the live outage was a **deploy gap** — production was still serving the
  prior commit `f1f1b46`, which introduced the crashing call. `b70b50d` is a
  code-only change and requires no database migration (migration `022` belongs
  to the already-deployed `f1f1b46`).
- Added regression coverage: null/undefined-user cases for `isOwnOrganizerEvent`
  in `tests/workspace-switching.unit.test.js`, and a DB-free
  `tests/event-details-guest-render.unit.test.js` that drives the real
  `getEventDetails` with a guest request and asserts a 200 render.
- Deploy action (redeploy `b70b50d` and verify a signed-out `HTTP 200`) tracked
  for the auto-deploy pipeline.
