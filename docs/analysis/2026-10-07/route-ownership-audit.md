# Route ownership audit — 2026-10-07

Static review of every Express route (486) on `feat/dialog-consistency`. For each route: where the caller's right to the resource ID is enforced. DB-free; no requests were made against any environment.

## Summary

- **Caller identity** always comes from the server-side session (`req.session.userId`, `res.locals.user` loaded from it). No route uses a request-supplied `userId` as the acting user. Request `userId` values appear only as *targets* on admin routes (delete user, remove group member) and as public profile lookups (`/runners/:userId`).
- **Findings:** one confirmed IDOR affecting 4 variant routes (2 organizer, 2 admin). **Fixed** in the same change as this report; regression test `tests/shop-variant-ownership.unit.test.js`.

### ✅ Fixed — organizer shop variants: cross-event IDOR

`PATCH|DELETE /organizer/events/:eventId/shop/products/:productId/variants/:variantId`

The middleware proves the caller manages `eventId` and that `productId` belongs to it, but `variantId` is never checked against `productId` before writing. `updateVariant` / `deactivateVariant` ([variant.service.js:47](../../../src/services/shop/variant.service.js#L47), [variant.service.js:70](../../../src/services/shop/variant.service.js#L70)) run `UPDATE … WHERE id = variantId`; the controller compares `variant.product_id` only after the update has committed ([organizer-shop.controller.js:192](../../../src/controllers/organizer-shop.controller.js#L192)), then returns 404 — the change is already persisted.

Variant UUIDs are published in the public product page ([product-detail.ejs:95](../../../src/views/pages/product-detail.ejs#L95)). Any account with organizer-workspace access and one product of its own can change price, stock, or deactivate another organizer's — or HelloRun's platform — variants.

**Resolution:** `updateVariant(productId, variantId, payload)` and `deactivateVariant(productId, variantId)` now require the product and include `product_id` in the UPDATE's WHERE clause; a foreign variant matches no row and the controllers return 404 with nothing written. The admin variant routes (same pattern, admin-only) take the same fix. The unit test fails against the previous code and passes against the fix.

### Hardening notes (not exploitable today)

- `canViewShopOrder` ([shop-access.middleware.js:111](../../../src/middleware/shop-access.middleware.js#L111)) admits any `organiser` when the order belongs to the `eventId` in the URL, without checking the organiser can access that event. It is safe only because every route places `canManageEventShop` first.
- `DELETE /blog/:slug/comments/:commentId` checks author/admin but not that the comment belongs to `:slug` ([blog-comment.service.js:472](../../../src/services/blog-comment.service.js#L472)).
- Timing-system webhook uses one platform-wide HMAC secret; any holder can post results for any `event_id`.
- `POST /organizer/events/:id/badges/:badgeId/image` uploads to R2 before confirming the badge exists (orphaned object on a bad ID).
