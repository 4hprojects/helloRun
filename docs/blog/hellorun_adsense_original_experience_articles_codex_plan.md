# HelloRun AdSense Content Strengthening Plan

## Purpose

Create a set of strong, original HelloRun articles that directly address the AdSense "Low value content" concern by demonstrating first-hand experience, platform-specific knowledge, original screenshots, real submission examples, actual review workflows, and useful participant guidance.

These articles must not read like generic running blog posts.

They should show that HelloRun is an active virtual-run platform with its own verification process, participant workflows, event operations, submission patterns, and lessons learned from actual usage.

---

# Primary Goal

Publish a focused cluster of HelloRun-first articles that:

- Demonstrate original experience and subject-matter knowledge
- Use first-hand platform evidence where available
- Include real HelloRun screenshots
- Include anonymized accepted and rejected proof examples
- Explain actual platform workflows
- Document common participant mistakes
- Provide practical participant guidance
- Support internal linking across HelloRun
- Strengthen site quality before the next AdSense review
- Add long-term SEO value beyond the AdSense review

---

# Important Content Rules

## Do

- Write from HelloRun's actual platform perspective
- Use first-person plural where appropriate, such as "we review" or "we found"
- Ground claims in real HelloRun workflows and evidence
- Use actual screenshots from the HelloRun platform where relevant
- Use anonymized real submission examples where available
- Explain why a submission was accepted, rejected, or questioned
- Use actual event examples where relevant
- Include original observations from reviewing participant submissions
- Include actual event statistics where available
- Link to relevant HelloRun event, submission, registration, or guide pages
- Include clear participant takeaways
- Use descriptive image alt text
- Add a useful FAQ where it strengthens the article
- Add Article structured data if the site's current content architecture supports it
- Preserve HelloRun's existing design system and blog layout

## Do Not

- Invent statistics
- Invent user behavior
- Invent review rules
- Invent screenshots
- Invent rejected or accepted examples
- Invent internal links
- Invent platform features that do not exist
- Pad articles to reach an arbitrary word count
- Produce generic AI-style running advice
- Repeat the same explanations across all articles
- Publish unsupported claims about fraud or cheating
- Expose participant names, email addresses, account details, precise locations, or sensitive data
- Use screenshots containing unredacted personal information

If a required fact, screenshot, statistic, or workflow detail is unavailable, leave a clear implementation placeholder instead of fabricating content.

Use this format:

`[NEEDS HELLO RUN DATA: describe exactly what is needed]`

# Article 1

## Title

What We Learned From Reviewing Virtual Run Proof Submissions

## Suggested Slug

`/blog/virtual-run-proof-submission-lessons`

## Search Intent

Informational and experience-based.

The article should help participants understand common submission issues while demonstrating HelloRun's first-hand operational experience.

## Core Angle

This article must be based on lessons observed while reviewing real virtual-run proof submissions on HelloRun.

It should not become a generic "how to submit running proof" guide.

## Suggested Structure

### Introduction

Explain that reviewing virtual-run submissions reveals recurring patterns that are easy to miss when designing an event.

Briefly explain why proof quality matters to participants and organizers.

### 1. What HelloRun Reviews in a Submission

Explain the actual information HelloRun reviewers check.

Examples may include:

- Distance
- Activity date
- Activity type
- Screenshot readability
- Event eligibility period
- Required supporting information
- Duplicate activity indicators

Only include checks that are actually part of the platform workflow.

### 2. The Most Common Submission Problems We See

Use real patterns from HelloRun.

Possible categories:

- Cropped screenshots
- Missing distance
- Missing date
- Unreadable metrics
- Wrong activity type
- Submission outside event period
- Duplicate proof
- Screenshot that does not contain enough information

Each issue should include:

- What the problem looks like
- Why it creates a verification problem
- How the participant can fix it

### 3. Examples From Real HelloRun Submissions

Add anonymized examples.

Recommended format:

#### Example A: Accepted

- What was visible
- Why it was sufficient
- Screenshot

#### Example B: Needs Clarification

- What was missing
- Why it was questionable
- Screenshot

#### Example C: Rejected

- What rule was not satisfied
- What the participant should submit instead
- Screenshot

Use only real examples.

### 4. What Surprised Us

Include actual unexpected patterns observed during review.

Possible prompts:

- Did participants crop too aggressively?
- Were dates frequently missing?
- Did users submit screenshots from app screens that reviewers did not expect?
- Did some apps display distance differently?
- Were multiple screenshots sometimes needed?

Use only real observations.

### 5. How These Lessons Changed HelloRun

Explain whether HelloRun updated:

- Submission instructions
- Event mechanics
- Reviewer workflow
- UI
- Screenshot guidance
- Validation messaging
- Error handling

If no product change has happened yet, explain what could be improved without implying it has already been implemented.

### 6. Participant Checklist Before Submitting

Create a practical checklist based on real HelloRun requirements.

### 7. Final Takeaway

Reinforce that complete, readable proof helps participants receive faster and more accurate review.

## Required Original Evidence

- At least 2 to 4 anonymized real examples
- At least 1 actual HelloRun interface screenshot
- At least 3 observations based on actual review experience
- Internal links to relevant event or submission pages

## Optional Data

If reliable data exists, include:

- Number of reviewed submissions
- Most common issue
- Percentage requiring correction
- Most-used activity apps

Do not include any metric that cannot be verified.
